## 3. 阶段 A 设计要点（大脑引擎）

- 位置：`Assets/LingGuangV05/XingGuang/Core/Brain/`，纯 C#，不依赖 Unity，可序列化进 `GameState.labState`。
- **元素**：字符串 id，如 `弧`、`弧@2,1`（绑定位置）、`字:明@3`、`且`、`关机`、`语气:皮`。架构决定同一张卡给出哪种元素：全连 = 绑定绝对位置；局部共享 = 去掉位置，只保留相邻关系；回环 = 相对位置链。
- **概念**：一组元素（key）、层数、权重 w（指向“是”）、活跃度 s。层 1 = 单个元素；层 k 由两个下层概念合成。
- **连接**：两个概念之间的强度；超过阈值生成上一层概念。
- **规则**：
  - R1 拉：误差 × lr × g^(读出层 − 本层)；
  - R2 合：够得着的同卡概念对，连接 += lr × |误差| × g^(层数上限 − 本层)，所以阶跃（g=0）合不出新概念；
  - R3 挤：板块格子数 = 宽 × 层；满了就挤掉最弱的概念，或与最相似的概念叠进同一格；
  - R4 衰：每张卡所有 w、s × (1 − d)；
  - R5 噪：自动标注按检查点错误率翻转标签；碰巧同现的元素照样被 R2 连起来；
  - R6 够：由连接方式决定哪些概念对够得着，以及序列每步的衰减（RNN ×.75，门控 ×.97）。
- **读出**：用匹配到的最高层概念加权作答；一个都匹配不到就按种子瞎猜。没题时，最强概念自己亮起（涌现用）。
- **准确率**：每个数据集用独立种子生成一组测试卡（不参与训练），按测试卡算准确率。
- **现象检测**：异或不可分、梯度消失、死记硬背、顿悟、泛化、越深越差、捷径偏见、长句失忆、灾难性遗忘、迁移、幻觉（叠格）等，只做检测，不写触发逻辑。
- **性能**：每张卡只看自己元素索引到的概念；每个板块的格子上限按 v1.1 §13 取 64–512；训练按批处理。

### C · 墙与突破（2026-10-04 完成）

- **规则**（`Core/XgSim.Walls.cs`）：一个阶段号（两条线共用），只有过墙才前进。
  - 每个阶段在练满一定轮数**并且**在本阶段待满一定时间后撞墙（第 1 阶段还要求任一数据集到 C 级）：练习轮数 40 / 120 / 300 / 300 / 300，时间 8 / 10 / 20 / 20 / 20 分钟（每阶段是一个月，墙在月底出现）。
  - 墙出现后，它的数据集在训练页可选，不用标注；墙的考核固定按 1 级难度出卡。
  - 用黄金参数让墙数据集的测试准确率达标，立刻进入下一阶段：

    | 阶段 | 墙 | 数据集与门槛 | 黄金参数 |
    |---|---|---|---|
    | 1 | 异或 | 异或 ≥ 90% | 层数 ≥ 2 · 激活 S 形 · 学习率 0.1–0.5 |
    | 2 | 梯度消失 | 手写 ≥ 85%、弹幕 ≥ 90% | 手写用局部共享（卷积），弹幕用回环（循环） |
    | 3 | 长句失忆 | 长句 ≥ 70% | 门控回环 · 梯度裁剪开 · 学习率 ≤ 0.01 |
    | 4 | 翻译不了 | 翻译 ≥ 85% | 编码器+解码器 · 宽度 ≥ 256 |
    | 4 附加 | 越深越差 | 视觉线任一数据集 ≥ 85% | 20 层以上 · 跨层直连（不结束阶段） |
    | 5 | 串行瓶颈 | 串行瓶颈数据集 ≥ 85% | 注意力 +「只用注意力」+ 位置标记 |

  - 秘籍节点（`secret.1/2/3/4/deep/6`）在撞墙后出现，买下才写明黄金参数和“为什么”；技能树里同时列出它要用到的节点。阶段 5 不卖秘籍。
  - 自悟：没买秘籍就过墙，发秘籍价 × 1.5 的奖金并点亮金边；阶段 5 在 AI 说出“只用注意力”之前自己配出来，奖金 ¥10,000。
  - 涌现（每个阶段一定发生）：1 寒冬里停训 60 秒或改层数（“？”格亮起「否」）；2 第一次泛化；3 过墙时它自己写一句诗；4 主动叫你（对话页做好后接真实条件）；5 注意力练满 8 轮后它说「如果只用注意力呢？」。没触发的在离开阶段时补上。
  - AI 寒冬：异或墙立着时订单收入减半，HUD 显示“寒冬”。
  - “？”格：新档和旧档都种下「关机 → 否」。第 1 阶段逻辑桌偶尔（最多 5 张）出 SI 预埋题「电脑正在更新，此时应该关机吗？」，答什么都算对，答案就是拉“？”格的方向。

### G · 对话与养成（2026-10-04 完成）

- **对话页**（exe 新增「对话」标签，`XgChatPage`）。阶段决定说话的形式，见 §11.5：

- **大脑注入**：每轮的系统提示都从概念盘生成（`XgSim.PersonaPrompt`），包括：

- **性格三轴**：温度 / 玩心 / 主见，各是语气板块上的一对元素。
  - 实际值 = 50 + 50 ×（高 − 低）/（高 + 低 + 0.5）。分母里的 0.5 是试玩后加的：没有它，开局种下的一张卡就把三条轴都推到 100。

- **涌现 4**：语气盘上「称呼」概念够强、而且 5 分钟没跟它说话时，它主动开口，用当下最强的语气说「{称呼}，你今天还没跟{自称}说话」。
- **三体彩蛋**：
  - 连说三次「不要回答」，它回「……好。」，然后沉默 1 分钟，面板显示「监听中」；

## Real MLP highlight and chance hint (2026-10-05)

- **The one real training** (design §11.8.1, §13; `XgTinyNet.cs` in Core, `XgRealTrainPanel` in Desktop).
  - Pure C#, deterministic (own xorshift seed, same under Mono and .NET), no Unity.
  - Pictures are 8×8: the four XOR pictures (left half lit = A, right half lit = B) and hand-drawn digits for "is it a 0?" (shifted, uneven ink, stray pixels).
  - Three lessons:
    - `XorPerceptron`: one layer, step output, Rosenblatt's rule; 65 parameters. The error jumps between 25% and 75% and never reaches 0.
    - `XorMlp`: 4 S-curve units, backpropagation; 265 parameters. The error falls to about 0.02 and all 4 pictures are right.
    - `Zero`: 3 S-curve units; 199 parameters. It learns 60 digits, gets 97% of 40 unseen ones, and answers "0" (93%) for the 0 of 0.txt, which is never in any training set.
  - Each run takes a few milliseconds; the panel spreads it over 4.5–5.5 s so the player watches the real curve.
- **Where it shows:** a corner panel of 灵光.exe, above the toast, never full-window.
  - The XOR wall rises (`WallObserved("combo")`): the perceptron that cannot get there.
  - Stage one is passed (`StageAdvanced(1)`): the two-layer net, drawn over the grey perceptron curve. It comes after the wall, so it never gives the golden setting away.
  - The stage-two emergence (`Emerged(2)`): "is it a 0?", ending on the 0.txt zero with a gold frame.
  - Contents: the input pictures with the net's live yes/no and ✓/✗, the live error curve, each unit's 64 weights as a blue/red 8×8 grid, a caption in plain words and the footer 「只有这一段是真训练：N 个参数，算了 M 毫秒。后面的阶段太大，游戏里改用模拟。」. Hover tips on all three areas.
  - 「跳过」 closes it at once. It waits while 灵光.exe is hidden or an insight card is up, and closes itself 9 s after the run ends. It never touches the sim.
  - `XingGuangView.Build` installs it with one line next to `XgHoloCard.Install`.
- **Chance hint on the guide note** (`XgChanceHint.cs`; one line in `XgGuide.Current`).
  - Fires when the run's test accuracy has stayed near chance for 6 epochs with unchanged settings. Near chance means: on average under 20% of the way from `chanceError` to `floorError`, never above 35%.
  - Changing any knob restarts the count, so the note goes quiet while the new setting trains.
  - It names the most likely knob, in this order, and rings its control:
    - learning rate too high (tears the board): `label:<one notch lower>`;
    - 阶跃 on two or more layers: `label:ReLU|S 形` (or the S-curve node if none is owned);
    - fully connected on an image or ordered-text desk while a fitting architecture is owned: that architecture's button;
    - every cell full: `name:Width` (or the next width node at the cap);
    - rate ≤ 0.01 with the board half empty: one notch higher;
    - otherwise: change one knob at a time.
  - Its text says what the player sees and why, for example 「「手写数字」测试准确率 18%，瞎猜也有 10%，已经 8 轮没起色。格子 64/64 全占满了……」.
  - It never gives away a golden setting. If the current stage's wall (standing or about to stand) checks the run's dataset and the run lacks the golden setting, it stays quiet, and the wall's own hints take over. The only exception is a sure cause (rate, step activation) whose fix alone still falls short of the golden setting.

## Data economy (2026-10-05)

Design v1.1 §11.8.3, §11.8.4, §11.8.7 and the §13 rows for the junk-pack factors and `logPerSec`.

- **Data sources** (`Core/XgSim.DataSources.cs`).
  - Every dataset can have several `XgDataOffer`s. The `source` is 公开包, 淘货杂包, 众包标注 or 剧情数据. Each offer also has `noise`, `month` (yyyymm, compared with the game calendar or the stage's month, whichever is later) and `downloadSec`.
  - **公开包**: one offer per skill-tree data node. The offer id is the node id (`mnist.pack`), so buying from 淘货 or from the tree is one purchase. Noise is 0–2% per dataset.
  - **淘货杂包**: 13 packs with 2016 names, such as 「百万条微博语料，爬虫新鲜货」, 「十万表情包打包」 and 「12306 验证码截图大全」.
    - Each costs ×0.3 of the public pack, has ×2 the samples and 20–40% noise.
    - A pack goes on sale in its month, once the dataset's stage is reached.
    - Big packs come down through 迅雷 at 1.5× the public download time.
  - **众包标注**: post a task for a desk on 摆渡众包, as the client this time. It needs the crontab node.
    - It brings 12 labels/s at ¥0.04 each, with 5% (vision) or 8% (text) wrong.
    - The task is taken down when the money runs out.
  - **剧情数据**: 老周 offers two packs, each once, the first time it can be bought.
    - Stage 4: ImageNet through his edu mail, ¥600 instead of ¥4,000.
    - Stage 5: the UN parallel corpus off the campus network, ¥1,500 instead of ¥5,000.
    - Both are low-noise and hand over the public node, so the samples count once.
  - Owning a junk or story pack makes the dataset available (`Owns`). `Samples` = packs that finished downloading + hand labels + crowd rows + logs the model labelled right.
  - Downloads use the existing 摆渡云 list. Public and story packs are keyed by dataset id, as before; junk packs by offer id. `AccelerateOffer` is the super-member speed-up for any of them.
- **Noise** (R5).
  - Outside noise (`DataNoise`) is worked out from the owned packs, plus stored crowd mistakes, minus rows already cleaned. Old saves that own packs get their noise without migration.
  - The R5 share is (own mistakes + outside noise) / (all samples + own mistakes). The denominator is now all samples, not hand labels.
  - A little noise is drowned out: the share of pool cards flipped is share³ / 0.4², and equals the share from 40% up. So 2% flips 0.005%, 15% flips 2%, and 30% flips 17%.
  - Measured on the board (300 automatic epochs, 40k samples, 3 seeds):

    | Dataset | Clean | 30% junk | 30% junk + 数据清洗 | 2% public noise |
    |---|---|---|---|---|
    | 手写数字 | .773 | .548 | .753 | .770 |
    | CIFAR | .937 | .564 | .874 | .933 |
    | 弹幕 | .722 | .657 | .718 | .720 |

  - The legacy curve subtracts outside noise from the effective samples, the same way it subtracts own mistakes.
  - 近亲繁殖 still counts only the lab's own mistakes.
- **数据清洗**: a stage-3 research node (¥800), a sibling of 数据增强. It halves the noise of junk packs and crowd rows, including rows already owned. The existing 抽检 clean-up (`CleanNoise`) discards own mistakes first, then outside rows.
- **Pool size**: the fix is log-mapped coverage.
  - `BoardPoolSize`: up to 4,096 samples, nothing changes. Past that, the pool is 4,096 × (1 + ln(samples / 4,096)), capped at 65,536. A 60k pack gives about 15,100 cards; 1.2M gives about 27,400.
  - `BoardPoolAt`: the extra cards open one per 8 cards trained on that dataset. The board needs repeats to form concepts, and opening the whole pool at once slowed big datasets down. With the whole pool open, the bot took 36:18; the stage-4 translation wall took 8:43 instead of 1:35.
  - On these generators, accuracy beyond about 4k distinct cards is mostly capacity-bound. Big packs mainly save labelling time and add variety; they do not lift the ceiling much.
- **Data flywheel** (`Core/XgSim.Flywheel.cs`).
  - A signed contract that meets its threshold sends back `LogPerSec` = base income × 2 logs per second. Before stage 5 it is ×0.1. They go into a per-dataset 日志 pile, capped at 200k.
  - **By hand**: a right answer on a desk with logs labels one log. It is clean, counts for the combo and is worth 4 samples. The label page shows 「用户日志 +4 样本」.
  - **By the model**: a toggle per dataset labels about 400 × √compute logs/s. The noise is 1 − the deployed accuracy. Wrong rows become the lab's own noise, so careless auto-labelling leads to 近亲繁殖.
  - The first logs say they hold users' chats.

## AI memory book (2026-10-05)

From stage 5, the AI keeps a real memory: important things go into a memory book as short notes. Before it answers, the notes most similar to what was just said are put into its prompt.

- **Retrieval** (`Core/Chat/MemoryRetrieval.cs`, pure C#, namespace `LingGuangV05.Core.Chat`). It is used both by the lab AI and by 晴雯's prompt.
  - `MemoryTokens`: CJK unigrams and bigrams, lowercase English words and digit runs. Function characters (的 了 我 你 主 人 …) are not unigrams, and a bigram made only of them is dropped.
  - `Bm25Scorer`: Okapi BM25 with k1 1.2 and b 0.75. The corpus counts as at least 8 notes, so a tiny book still has usable idf. English words weigh 2.
  - Relevance rule: a note counts only if it shares a bigram, an English word, or two different characters with the query, and its score is ≥ 2.5. Anything else scores 0, so 「在吗」「今天天气不错」 recall nothing.
  - `MemoryRanker.Rank`:
    - drops scores under 30% of the best;
    - adds +10% per importance step and up to +15% for recency (half-life of about 14 calendar days);
    - the boosts only reorder notes that already passed the relevance rule.
  - `RelevantThenRecent` fills the remaining slots with the newest notes (used for 晴雯).
  - `IMemoryScorer` is the seam for an embedding scorer. One could call llama-server `/v1/embeddings` with a small separate GGUF such as Qwen3-Embedding-0.6B and return cosine minus a cut-off. No model has been downloaded and nothing ships for this.
- **Book** (`XingGuang/Core/XgSim.MemoryBook.cs`, saved in `XgState`):
  - Fields: `memoryBook` (`XgMemoryEntry`: id, text, subject 主人/晴雯/老周/它自己/世界, importance 1–3, createdDay yyyymmdd, createdAt, lastUsedAt/lastUsedDay, uses), `nextMemoryId`, `memoryMigrated`, `memoryRecalled` (ids used for the last 对话 answer), `memoryRecallQuery`, `memoryRevision`.
  - Cap of 200. The note evicted first is the one with the lowest importance × (1 + 0.1·uses) / (1 + age in days / 30).
  - Old saves: the `S.memory` lines (「你说过：…」) are moved once into `主人说：…` notes, with duplicates merged. Their date is filled in when the calendar becomes known. `S.memory` stays empty afterwards.
  - `AddLine` no longer writes memory. The finale's question 4 and its fallback, and the offline `Earlier()`, now read the book.
- **Writing (mem0-style extract → update)**. This is our own C# version of the memory update loop in mem0 (github.com/mem0ai/mem0, Apache-2.0), credited in the code comment. No source or prompt text was copied, so no THIRD_PARTY_NOTICES entry is needed.
  - After a stage ≥ 5 answer, on the 对话 page (`XgChatPage.Answer`) and from the YY 灵光 contact (`YYChatHub.Reply`), `LocalLLM/LlmMemory.AfterExchange` sends one request through `Chat()`. It is queued after the visible reply is already on screen, and only when `!llm.ChatBusy`. The call sits in a single `Send` helper so that it can move to llm-tune's background lane in one line.
  - Request: `MemoryExtractionMessages` (the exchange plus the top 5 similar notes with ids), `MemoryGrammar` (GBNF: `{"ops":[op(,op)?]}`, op ADD|UPDATE|DELETE|NONE, a fixed subject list, importance 1–3, bounded text), T 0.2, 120 tokens, thinking off.
  - Code checks the answer before applying it:
    - at most 2 ops;
    - text cleaned and cut to 30 characters (64 for English notes);
    - 「无值得记录…」 rejected;
    - UPDATE and DELETE only on ids the extractor was shown;
    - an ADD that repeats a note refreshes it instead;
    - promises are at least importance 2.
  - Offline rule, used when there is no model, the model is busy, or the request failed: the owner's line must be ≥ 6 characters, carry a cue (要/想/会/明天/下周/喜欢/讨厌/答应/生日/考试/面试/打算… and English cues), and not be a question to it. It becomes 「主人说：…」, with importance 2 for strong cues.
- **Recall**:
  - `PersonaPrompt(month, hot, query = null)` injects only the relevant notes (≤ 5) as 「你记得：…」, built from the owner's last two 对话 lines with the previous line at weight 0.5.
  - Each recalled note's uses and lastUsed are updated; a retry with the same query counts once.
  - The YY 灵光 system prompt (`LlmPersonas.Conversation`, stage ≥ 5) gets the same line from its own last two lines.
  - 「让它代我回」 recalls for her message without moving the 对话 panel.
- **晴雯**: `GirlfriendPromptText.System(..., latest)` and `PromptMemories(s, latest)` pick her 8 memories most relevant to his latest line, then the newest ones, in the order she learnt them. Her memories stay in `GirlfriendState`; only the scorer is shared.

## Local LLM tuning (2026-10-05)

Goal: faster and sturdier local replies (Qwen3.5-4B Q4_K_M through llama.cpp's llama-server). Replies still arrive whole; there is no streaming.

- **Server flags** (`Core/Chat/LlmScheduling.ServerArgs`, owned server only):
  - `-c 4096×N -np N --fit on --fit-ctx 4096 --flash-attn auto --cache-type-k q8_0 --cache-type-v q8_0 --cache-reuse 256 --cache-ram 2048 --ctx-checkpoints 6 --checkpoint-min-step 64 --jinja --reasoning-budget 0 --verbosity 4`.
  - The layer count is no longer forced (`-ngl 99` used to switch `--fit` off). llama.cpp now puts as many layers on the GPU as fit and keeps the rest on the CPU.
  - stdout/stderr are read: the `offloaded N/M layers to GPU` line is logged, and a partial or CPU layout shows 「显存不够，部分在内存里跑，会慢一些」 on the 对话 status line (`LocalLlm.Detail`).
  - Start ladder when the server exits during startup: GPU+fit → the same with an f16 KV cache → CPU only (`--n-gpu-layers 0 --device none`).
  - If an owned server dies, it restarts once (again only after 10 min). Callers get `done(null)` and offline lines in the meantime.
  - The largest real prompts measured 803 tokens (对话 stage 6, 20 messages) and 1023 tokens (林晴雯, 12 lines + few-shots), so 4096 per slot leaves room. The YY history budget went from 4800 to 2400 characters to stay inside one slot.
- **Slots and priority** (`LocalLlm`, `LlmScheduling`):
  - Three slots normally, four with parallel judging. Each character keeps a fixed slot (`id_slot`): 0 = 灵光 (对话, YY 灵光, stand-in, love question, finale), 1 = 林晴雯, 2 = everyone else and background work.
  - An external server on 18088 is never managed. Its `/props` slot count decides whether requests are pinned (3+ slots) or left to the server.
  - The QA harness keeps its 1/4 unpinned layout.
  - Visible chat goes first. Background work waits while a visible reply is queued or running, or while the player types into a focused TMP/uGUI input; UI Toolkit fields can call `NoteTyping()`. Background work covers judges, card comments (`ChatBackground`), 巨信 auto-replies, her proactive messages, the memory extractor (`LlmMemory.Send` → `ChatBackground`) and warm-ups.
  - Time budgets run from queueing: 20 s visible, 40 s background, ×3 when the model runs partly or fully on the CPU. Then `done(null)`.
  - With parallel judging, game judges use slots 3 and 2 (two at a time) and never take a character's slot.
- **Warm-up** (`LlmWarmup`): when idle, each character slot gets one 1-token request with that slot's stable prefix: 对话's system message, and her system message plus few-shots. The first real reply then only processes the conversation. Warm-ups are background, aborted if their slot is needed, and re-sent at most every 30 s when the prefix changes.
- **Prompt layout** (`Core/Chat/LlmPromptLayout`):
  - Qwen3.5 is a hybrid recurrent model. `--cache-reuse` is ignored, and the server can only resume from checkpoints it saves at the start of the last user message. A turn is therefore cheap only if the new prompt extends the previous one.
  - So every builder now sends a byte-identical system message (persona, rules, slowly changing board/tier) and a history that only grows. The history window moves in steps of half its size (it shows between limit and 1.5× limit lines), not one line per turn.
  - Everything that changes per turn goes in a 「【当前状态（只给你参考，不要复述）】」 block in front of the last user line:
    - 对话 / stand-in: tone and leanings, recalled memories, recent replies, retry note, stage-2 options.
    - 林晴雯: clock, activity, mood, memories, plans, holiday and situation.
    - YY: 老周's live numbers, the group's topic, 灵光's sample counts, memories, recent replies.
  - Builders were split for this: `XgSim.PersonaCore / PersonaBoard / PersonaTone / PersonaMemory` (`PersonaPrompt` = all four), `GirlfriendPromptText.Stable / State` (`System` = both), `GirlfriendPrompt.Prefix`, `XgChatPage.StableSystem` and `LlmPersonas.State`.
- **Measured** (this Mac, M2 Max; test server on :18190; :18088 untouched):
  - Startup to /health: 1.8 s → 1.0–1.4 s.
  - First reply with warm-up: 对话 prompt eval 1.2 s → 0.58 s; 林晴雯 1.1–1.5 s → 0.39 s.
  - Simulated low VRAM (`--fit-target`, 10 of 34 layers on the GPU): starts in 4.1 s. First reply 15.0 s → 7.4 s, hers 20.2 s → 5.6 s.
  - CPU-only fallback: starts in 2.2 s and answers. First reply 8.3 s with warm-up, steady turns 1.8–4.7 s.
